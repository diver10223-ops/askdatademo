# 产品V2.0数据库迁移与账号边界

## 基线

- 通用逻辑模型：PostgreSQL兼容SQL；仓库内使用H2 PostgreSQL模式验证。
- 版本工具：Flyway，迁移文件只追加，不修改已发布版本。
- 客户方言：在M8按数据库产品建立独立location和验证流水线，不在通用迁移中散布客户条件分支。
- 生产环境禁止应用启动账号执行DDL；Flyway使用独立迁移连接。

## 账号矩阵

| 账号 | DDL | 平台DML | 查询 | 凭据变量 |
|---|---|---|---|---|
| `askdata_migration` | 仅部署窗口允许 | 初始化/迁移 | 是 | `ASKDATA_MIGRATION_DB_*` |
| `askdata_app` | 禁止 | 授权业务表 | 是 | `ASKDATA_PLATFORM_DB_*` |
| `askdata_readonly` | 禁止 | 禁止 | 授权视图/表 | 独立运维工具注入 |

账号示例见`deploy/database/postgresql/create-roles.sql.example`。脚本只包含psql变量，不包含任何默认生产密码。角色创建、密码注入和授权须由客户数据库安全管理员执行并进入审计。

## 标准升级

1. 校验目标环境、备份/快照、当前Flyway版本及迁移文件SHA256；阻止含未提交迁移的发布。
2. 停止管理写流量或进入兼容写窗口，使用迁移账号执行`flyway validate`和`migrate`。
3. 重新授予新表/序列的应用与只读权限；立即撤销迁移账号的临时网络访问。
4. 使用应用账号执行健康、最小CRUD和“禁止CREATE TABLE”检查。
5. 启动服务并观察错误率、迁移版本、主从延迟及审计事件。

## 前滚恢复而非破坏性降级

已发布迁移不提供自动`undo`。失败时按以下顺序处理：

1. 在允许的兼容窗口内修复为新的前滚迁移；
2. 若新结构造成不可接受风险，停止写入并恢复升级前数据库快照；
3. 用原版本应用验证恢复点，再用修正后的新迁移从该恢复点前滚；
4. 对比表数量、Flyway历史、核心行数和配置快照哈希。

仓库内H2测试证明空库迁移可重复且应用账号无DDL权。PostgreSQL/MySQL的真实备份恢复、主从和权限证据属于M8客户环境验收，未执行时不得宣称完成客户交付。
