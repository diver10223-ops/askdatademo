# 产品 V2.1—V2.3 开发、测试、验收与发布规划

> 目标：依次完成 V2.1、V2.2、V2.3 的开发、测试、验收和发布；每个版本维护演示、POC、产品、客户交付四种状态；任何新版本开发不得覆盖或破坏历史版本，当前版本和各历史版本均可随时获取、验证和恢复。客户交付状态在有具体客户后按需派生，当前为空。

## 1. 总体结论

V2.1、V2.2、V2.3 均按四种状态管理：

| 形态 | 用途 | 数据与依赖 | 交付物 |
|---|---|---|---|
| 演示版（Demo/Offline） | 产品演示、汇报、无环境快速体验 | 内置脱敏 Fixture；不依赖外部模型、数据库、网络或服务端 | 单文件 HTML、版本说明、场景清单、校验值 |
| POC 版 | 客户环境联调、能力验证、真实链路试用 | 可配置模型与数据库；默认不内置客户凭据；允许受控演示数据兜底 | 前后端运行包、部署配置、初始化数据、接口契约、操作与验收手册、校验值 |
| 产品版（Product） | 正式部署、生产运营和持续运维 | 连接正式认证、模型、数据库和基础设施；禁止演示数据静默兜底 | 生产安装包/镜像、迁移与回退包、安全与运维手册、SBOM、审计及验收证据、校验值 |
| 客户交付版（Customer Delivery） | 针对具体客户实施、上线和验收 | 从已发布 Product 派生，叠加客户环境、业务口径、品牌、集成和合规适配；客户配置与凭据隔离保存 | 客户交付包、差异清单、部署参数、数据映射、客户测试证据、验收签字和运维移交材料 |

同版本的 Demo、POC、Product 共享功能定义、交互口径、核心契约和版本号。Demo 用于确定性展示，POC 用于能力验证，Product 是通过产品门禁的环境中立标准产品。Customer Delivery 必须从已发布 Product 派生，一个产品版本可以对应零个、一个或多个客户交付实例。四种状态不得互相改名替代。

## 2. 版本与交付矩阵

| 产品版本 | 核心范围 | 演示版 | POC 版 | 产品版 | 客户交付版 | 历史版本状态 |
|---|---|---|---|---|---|---|
| 当前稳定基线 | 现有一期/二期问数能力 | 永久保留，可离线打开 | 永久保留，可独立启动 | 按现状标注，不补写未通过的生产能力 | 空 | 冻结，只接收严重缺陷和安全修复 |
| V2.0 | 企业级可信问数底座 | `2.0.x-demo` | `2.0.x-poc` | `2.0.x-product` | 当前为空，有客户后派生 | V2.1 开始后转维护状态 |
| V2.1 | 多任务优化、用户体验、多任务执行 | `2.1.x-demo` | `2.1.x-poc` | `2.1.x-product` | 默认为空，有客户后派生 | 发布后形成不可移动基线 |
| V2.2 | 智能分析、主动服务 | `2.2.x-demo` | `2.2.x-poc` | `2.2.x-product` | 默认为空，有客户后派生 | 发布后形成不可移动基线 |
| V2.3 | 单域数据扩展、企业治理、生态开放 | `2.3.x-demo` | `2.3.x-poc` | `2.3.x-product` | 默认为空，有客户后派生 | 发布后形成不可移动基线 |

版本号规则：`2.1.0` 表示首次产品发布，`2.1.1` 表示兼容性缺陷或安全修复；Demo、POC、Product 必须对应同一产品版本和可追溯源码基线。客户交付实例另加客户标识与交付修订号，例如 `2.1.0-customer-a-r1`，但不得改变其产品基线版本。

### 2.1 V2.0 当前四状态说明

V2.0 同样按 Demo、POC、Product、Customer Delivery 四种状态管理，但“存在建设内容”不等于“已经正式发布或交付”：

| V2.0 状态 | 当前基础 | 当前结论 | 正式关闭条件 |
|---|---|---|---|
| Demo | 已有单文件 Offline Demo、内置 Fixture、稳定标签和演示场景 | 可恢复的稳定演示基线 | 从冻结标签重建正式 Demo 制品，完成断网验收、版本清单、SHA256 和远端归档 |
| POC | 已有 FastAPI POC、Phase 2 Provider 配置和联合测试能力 | 仓库内实现及协议仿真通过；真实客户环境验收未完成 | 完成真实模型、ClickHouse/MySQL、黄金问题、业务对账和客户签字 |
| Product | 已有 Java 控制面、Python 执行面、平台数据库、安全门禁、发布脚本及环境中立产品基线 | 产品基线候选已形成；尚未正式发布 | 完成长稳、容量、安全、运维、升级回退审查，以及正式标签、产品归档、SHA256 和发布批准；不以具体客户输入为前提 |
| Customer Delivery | 当前没有具体客户输入和交付实例 | 空 | 有客户后，从已发布 V2.0 Product 派生，完成客户环境、认证、数据、模型、网络、品牌、业务口径和验收适配 |

因此，V2.0 当前包含三个非空状态：Demo、POC、Product；Customer Delivery 为空。Demo 可稳定获取，POC 待真实环境验收，Product 待产品发布门禁关闭。后续先冻结 V2.0 三类标准制品，再以 V2.0 Product 正式标签作为 V2.1 开发起点；出现具体客户后再建立独立客户交付实例。

## 3. 如何保证当前演示、POC 和产品状态随时可获得

### 3.1 冻结源码基线

- 保留稳定分支 `release/v1-v2-test`，不把 V2.1 功能直接合入该分支。
- 保留不可移动标签 `v1-v2-poc-baseline-20260812`；任何人不得删除、覆盖或强制移动标签。
- 当前 V2.0 完成候选发布后，增加不可移动标签，例如 `product-v2.0.0`。
- 标签必须关联源代码提交、版本说明、测试证据和制品校验值。

### 3.2 冻结可直接使用的制品

不能只保留 Git 源码；还要保留无需重新开发即可使用的发布包：

```text
artifacts/releases/
├── current-baseline/
│   ├── demo/askdata-current-demo.html
│   ├── poc/askdata-current-poc.tar.gz
│   ├── product/askdata-current-product.tar.gz
│   ├── RELEASE_NOTES.md
│   ├── MANIFEST.json
│   └── SHA256SUMS
├── 2.0.0/{demo,poc,product,...}
├── 2.1.0/{demo,poc,product,...}
├── 2.2.0/{demo,poc,product,...}
└── 2.3.0/{demo,poc,product,...}
```

- Git 仓库只保存清单、说明和必要的小型交付物；正式压缩包应同步上传到受控制品库或 GitHub Release。
- 每个制品至少保留两份副本：远端发布存储一份，受控备份存储一份。
- `MANIFEST.json` 记录产品版本、形态、源提交、构建时间、工具链版本、数据库版本、场景基线和文件校验值。
- `SHA256SUMS` 用于下载后完整性校验。

### 3.3 一键恢复与定期复验

- 提供按版本下载、校验、解压和启动的命令，不依赖当前开发分支。
- 当前 Demo 每月至少执行一次离线打开和八场景回归。
- 当前 POC 每月至少从发布包执行一次冷启动、初始化、健康检查和核心场景回归。
- 当前 Product 每季度至少在隔离的准生产环境执行一次安装/升级、认证授权、安全、监控、备份恢复和回退演练。
- 复验失败不修改旧制品；从对应维护分支修复并发布补丁版本。

## 4. V2.1 演示、POC 和产品同步策略

### 4.1 共享能力基线

V2.1 Demo、POC 与 Product 共享以下内容：

- 同一套多任务问题、任务拆解规则和任务 DAG Schema。
- 同一套任务状态：待执行、运行中、成功、部分成功、失败、已取消。
- 同一套用户交互：计划预览、执行进度、节点详情、取消、重试、结果汇总和未核实项。
- 同一套指标、口径、角色权限和演示场景编号。
- 同一套前端组件和验收用例。
- 同一套公开 API/内部契约基线和数据库迁移序列。

Demo、POC、Product 的差异应集中在数据、执行适配、部署与治理层，不得分叉核心业务逻辑；客户交付只允许通过配置、适配器、扩展点和受控补丁实现差异，不得形成不可回收的客户私有主干：

- Demo Adapter：读取内置 Fixture，按固定时间线模拟串并行、失败、取消和部分成功，页面必须显示“模拟执行”。
- POC Adapter：调用 FastAPI/Java 控制面和 Python 执行面，可连接经配置的真实模型与数据库；演示兜底必须显式标识，禁止静默替代真实执行。
- Product Runtime：使用正式身份认证、角色与数据权限、密钥管理、TLS、审计、监控告警、容量保护、备份恢复和变更审批；禁止 Fixture 或模拟 Provider 进入生产路径。
- Customer Delivery：绑定客户、Product 基线版本和交付修订号，保存差异清单、客户配置引用、数据映射及验收证据；客户秘密和业务数据不得进入通用产品制品。

### 4.2 V2.1 必备演示场景

1. 一个问题拆成多个并行查询并汇总。
2. 前置查询完成后触发下钻或对比任务。
3. 用户在执行前调整任务计划。
4. 长任务展示实时进度并允许取消。
5. 单节点失败后重试成功。
6. 非关键节点失败，整体返回部分成功及未核实项。
7. 关键节点失败，不生成误导性的完整结论。
8. 多轮追问继承时间、机构、指标和任务上下文。

每个场景必须同时拥有 Demo Fixture、POC 测试数据、Product 准生产验收数据、自动化断言和人工验收步骤。

## 5. 分支、标签与开发隔离

### 5.1 建议分支

| 分支 | 用途 | 合入规则 |
|---|---|---|
| `release/v1-v2-test` | 当前稳定演示/POC | 仅严重缺陷、安全修复 |
| `release/product-v2.0` | V2.0 维护 | 仅 V2.0 补丁 |
| `develop/product-v2.1` | V2.1 日常集成 | 通过 V2.1 局部门禁后合入 |
| `release/product-v2.1` | V2.1 候选、验收和补丁 | 只接收发布修复 |
| `develop/product-v2.2`、`release/product-v2.2` | V2.2 开发与发布 | V2.1 正式基线创建后建立 |
| `develop/product-v2.3`、`release/product-v2.3` | V2.3 开发与发布 | V2.2 正式基线创建后建立 |

- 新版本分支必须从上一个正式版本标签创建，不能从带有未验收功能的工作区直接创建。
- 功能分支采用 `feature/product-v2.1-*` 等命名。
- 并行工作使用独立 Git worktree，避免构建产物、数据库和配置互相覆盖。
- 当前稳定版本的修复先进入对应维护分支，验证后再选择性前向合入新版本；新版本功能不得反向合入旧版本。

### 5.2 建议标签

- 正式源码标签：`product-v2.1.0`。
- 候选标签：`product-v2.1.0-rc.1`。
- Demo 制品：`askdata-product-v2.1.0-demo.html`。
- POC 制品：`askdata-product-v2.1.0-poc.tar.gz`。
- Product 制品：`askdata-product-v2.1.0-product.tar.gz` 或对应不可变镜像集合。

标签和制品均不可原地覆盖；修复后发布 `2.1.1`，不替换 `2.1.0`。

## 6. 数据、配置和运行环境隔离

- 每个版本使用独立数据目录，例如 `data/runtime/2.0`、`data/runtime/2.1`，不得让 V2.1 数据库迁移直接修改 V2.0 数据。
- 每个版本使用独立端口、容器名、数据库名和配置前缀。
- 数据库迁移只能前向执行；发布包内必须包含基线 Schema、迁移脚本、备份恢复说明和兼容性矩阵。
- Demo Fixture 按版本保存，例如 `fixtures/demo/2.1/`，不得只维护一个会被后续版本覆盖的 `latest` 文件。
- POC 配置模板不得含凭据；客户配置和运行数据不得进入发布包或 Git。
- “当前最新版”只能作为指向具体版本的索引，不能成为唯一制品。

## 7. 自动构建与制品发布流水线

每个候选版本必须从干净标签或候选提交自动执行：

1. 检查工作树、依赖锁定、版本号和契约兼容性。
2. 执行后端、前端、Java 控制面及数据库迁移测试。
3. 执行当前稳定版本回归，证明新开发没有破坏维护基线的构建能力。
4. 构建 Demo 单文件并扫描外部网络依赖。
5. 构建 POC 运行包并扫描凭据、运行数据和内部文件。
6. 分别从 Demo、POC、Product 三类标准制品做离线验证、冷启动和准生产部署验证；有客户交付实例时，另从客户交付包执行客户环境部署验收。禁止直接用源码目录替代制品验收。
7. 生成 `MANIFEST.json`、`SHA256SUMS`、SBOM、版本说明和测试报告。
8. RC 制品进入验收区；签字后原样晋升正式区，不重新构建。
9. 上传受控制品库/GitHub Release，并复制到备份存储。
10. 下载正式制品重新校验一次，更新版本索引。

必须避免“验收的是一个包，发布时又重新构建另一个包”。正式发布应晋升已验收 RC 制品，二进制校验值保持不变。

## 8. 各版本开发、测试、验收、发布顺序

### 8.1 V2.1

- 开发：多任务 Schema、规划、DAG 调度、任务状态、上下文和交互组件；同步实现 Demo Adapter、POC Adapter 和 Product Runtime 配置。
- 测试：单元、契约、DAG、并发/取消/重试、部分成功、前端交互、八类演示场景和 V2.0 回归。
- 验收：Demo 断网验收；POC 发布包冷启动；真实 Provider 联调；多角色权限、安全、审计和业务结果核对。
- 发布：先 RC，再分别完成体验验收、POC 验收和产品验收；同步发布 Demo、POC、Product。Customer Delivery 不随标准版本强制生成，有具体客户后按客户项目单独交付。

### 8.2 V2.2

- 从 `product-v2.1.0` 正式标签创建开发基线。
- 开发智能分析、异常归因、订阅预警和报告；Demo 增加可重复的历史序列与触发 Fixture，POC 增加调度和通知适配。
- 除 V2.2 专项验收外，完整回归 V2.1 多任务场景和当前稳定基线。
- 同步发布 `2.2.0-demo`、`2.2.0-poc` 与 `2.2.0-product`，继续保留 V2.1 制品。

### 8.3 V2.3

- 从 `product-v2.2.0` 正式标签创建开发基线。
- 开发单域 API/文档/实时数据接入、模型与成本治理、审计增强、标准 API、Webhook 和 SDK。
- 验收数据新鲜度、混合任务、配额、安全、扩展节点和外部集成，并完整回归 V2.1、V2.2 主场景。
- 同步发布 `2.3.0-demo`、`2.3.0-poc` 与 `2.3.0-product`，历史制品继续只读保留。

## 9. 发布门禁

任一版本同时满足以下条件才可正式发布：

- 功能范围和非目标已冻结，需求—代码—测试—制品可追踪。
- Demo、POC、Product 的核心功能、场景编号和业务口径一致；客户交付与 Product 基线之间具有完整差异清单。
- Demo 完成物理断网或等效断网验证，不包含外部运行依赖。
- POC 从干净发布包完成安装、初始化、升级、备份、恢复和卸载验证。
- Product 在隔离准生产环境完成认证授权、网络与传输安全、密钥管理、容量长稳、监控告警、备份恢复、数据库升级及回退验证。
- 自动测试、人工体验验收、业务结果验收、安全检查和回归均通过。
- 未关闭问题有明确分级；不存在 P0/P1 发布阻断问题。
- 版本、提交、数据库 Schema、契约、文档和校验值全部一致。
- Release Notes 明确新增、变更、已知限制、兼容范围和回退方法。
- Demo、POC、Product 三类标准制品都已上传并完成异地备份和下载复验；客户交付制品按客户隔离保存和授权访问。

## 10. 建议立即执行的基线保护工作

在启动 V2.1 功能开发前完成以下事项：

1. 整理当前未提交工作，明确哪些属于 V2.0 正式候选，禁止把脏工作区直接作为 V2.1 起点。
2. 从 `v1-v2-poc-baseline-20260812` 重建当前 Demo 与 POC，完成校验和冷启动复验；当前尚不满足产品状态的能力必须如实标注。
3. 完成 V2.0 当前候选的测试和分层验收，创建 `product-v2.0.0` 标签及 Demo、POC、Product 三类版本化制品。
4. 建立远端制品库和备份位置，禁止只依赖本机 `frontend/dist`、`frontend/offline-dist` 或 `artifacts/`。
5. 将现有 `v2-package-release.sh` 扩展为同时生成 Demo、POC、Product、Manifest 和版本化目录的通用发布脚本。
6. 建立“按标签重建”“从制品冷启动”和“准生产部署验收”三套自动化门禁。
7. 从 `product-v2.0.0` 创建 V2.1 开发分支和独立 worktree，再开始 V2.1 开发。

## 11. 责任与记录

- 每日修改统一记录到 `docs/DAILY_CHANGELOG.md`。
- 每个版本建立独立需求范围、执行计划、测试策略、验收报告、发布说明和已知问题清单。
- 每次发布记录批准人、发布日期、标签、提交、制品地址和 SHA256。
- 每季度抽查至少一个历史版本，证明其 Demo 可打开、POC 可安装；结果加入每日/运维记录。
