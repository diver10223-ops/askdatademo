# V2.1 多任务七层逻辑与全量修改影响分析

## 1. 结论

多任务会调整七层处理逻辑，但不推翻七层架构。七层职责仍然成立，主要变化是从“一个请求按 L1→L7 串行执行、L5生成少量SQL、L6顺序执行”升级为“一个请求产生版本化任务计划，计划内包含多个有依赖的任务节点，由L6按DAG调度，L7依据任务完整性和成功事实生成回答”。

V2.0 已有请求、会话、七层轨迹、SQL执行、Provider执行、SSE事件、结果快照、准入和取消数据，可继续复用；V2.1 必须新增计划、节点、依赖、尝试、事实和证据关系，不能只将DAG放入现有JSON，否则无法可靠完成查询、恢复、审计、重试和统计。

## 2. 七层处理逻辑变化

| 层级 | V2.0 现有逻辑 | V2.1 多任务调整 | 主要数据变化 |
|---|---|---|---|
| L1 交互层 | 接收问题、会话、身份，启动单请求 | 增加计划预览/确认/调整、取消、单节点重试命令；展示任务进度 | 请求控制命令、计划版本、用户确认记录 |
| L2 对话理解层 | 抽取单组指标、机构、时间、意图并预检权限 | 抽取多个分析目标、共享参数、输出要求；逐目标权限预检；识别需要澄清还是可以拆解 | `analysisGoals[]`、`sharedContext`、目标级权限决定 |
| L3 语义层 | 归一口径并形成单一语义计划 | 拆分子任务，定义依赖、关键/非关键节点、完整性规则、可并行组和计划版本 | `TaskPlan`、`TaskNode`草案、依赖和完整性策略 |
| L4 资产层 | 为本轮问题匹配表、字段、指标 | 为每个节点分别匹配并冻结资产版本；逐节点实施数据源、表、字段权限 | 节点资产绑定、时效、口径版本和权限证据 |
| L5 查询生成层 | 生成一个或少量顺序SQL计划 | 生成SQL/受控计算节点和可执行DAG；校验无环、输入输出类型、依赖和成本 | 可执行DAG、SQL模板版本、节点输入/输出引用 |
| L6 执行治理层 | 顺序执行SQL，支持请求级取消、有限重试和部分成功 | DAG串并行调度；节点级状态、attempt、重试、取消传播、恢复；按关键性裁决整体状态 | 节点状态、执行尝试、事件、不可变事实、整体完成度 |
| L7 结果解释层 | 基于本轮结果生成摘要 | 仅使用成功任务事实；逐结论绑定证据；披露失败、跳过和未核实项；不得把关键失败包装成完整成功 | 结论—事实引用、完成度、未核实项和回答版本 |

### 2.1 不变的边界

- 模型不裁决权限、SQL安全、DAG合法性、任务状态和最终完整性。
- L7不查库、不补数、不重算，不使用失败节点或无权节点的数据。
- 所有节点限定在单域、已发布资产和受控任务类型内。
- Product模式禁止Fixture静默兜底；POC使用模拟能力时必须显式标识。
- V2.1任务节点仅引用已发布SQL模板和受控计算；不引入普通用户开放式Text-to-SQL，模型SQL候选不得因添加“未经验证”提示而执行。

## 3. 数据库修改

### 3.1 复用现有表

| 现有表 | V2.1用途 | 调整建议 |
|---|---|---|
| `run_session` | 会话、角色和权限快照 | `context_json`保存最近确认计划和可复用事实引用；不保存完整DAG主记录 |
| `run_request` | 多任务请求主记录和总体状态 | 新增当前计划引用、任务统计和计划确认状态；保留请求级取消和准入字段 |
| `run_layer_execution` | L1—L7层级轨迹 | 继续记录层级汇总；不要用其代替任务节点轨迹 |
| `run_sql_execution` | SQL执行事实 | 增加任务节点/attempt关联；同一节点重试产生多个attempt，不覆盖历史 |
| `run_provider_execution` | 模型和数据源调用记录 | 增加task/attempt关联，便于计算单节点成本和故障 |
| `run_sse_event` | 请求级可续传事件 | payload增加planId、taskId、attemptId；事件序号仍按request单调递增 |
| `run_result_snapshot` | 最终回答与结果快照 | 保存最终EvidenceAnswer；节点原始结果改由执行事实表管理 |
| `audit_operation_log`及完整性链 | 用户操作和审计 | 增加计划调整、确认、节点重试、取消等动作 |
| `ops_retention_policy`、`run_fact_archive` | 在线保留和归档 | 加入新增任务表的保留与归档策略 |

### 3.2 建议修改现有表

`run_request`建议新增：

- `current_plan_id`：当前计划引用；建表顺序需要先允许为空，再加外键。
- `plan_status`：`DRAFT/WAITING_CONFIRMATION/CONFIRMED/EXECUTING/COMPLETED`。
- `total_tasks`、`succeeded_tasks`、`failed_tasks`、`skipped_tasks`、`cancelled_tasks`。
- `completion_ratio`：可由统计实时计算，若落库必须由服务端统一维护。
- `answer_version`：计划重试或结果更新后的回答版本。

`run_sql_execution`和`run_provider_execution`建议新增：

- `task_id`外键。
- `attempt_id`外键。
- `plan_version`或通过task关联计划版本。

`run_sse_event`无需强制增加列，可先在`payload_json`携带taskId；为了高频任务事件检索，可增加可空`task_id`和索引。

### 3.3 必须新增的核心表

| 新表 | 关键字段 | 作用与约束 |
|---|---|---|
| `run_task_plan` | `id, public_id, request_id, plan_version, status, plan_json, permission_snapshot_id, config_release_id, created_by, confirmed_by, confirmed_at` | 一个请求多个版本；`UNIQUE(request_id,plan_version)`；已确认计划不可覆盖 |
| `run_task_node` | `id, public_id, plan_id, node_code, node_type, critical, status, input_json, output_schema_json, timeout_ms, max_attempts` | 任务节点主记录；`UNIQUE(plan_id,node_code)` |
| `run_task_dependency` | `plan_id, upstream_node_id, downstream_node_id, dependency_type` | 保存DAG边；复合主键；发布计划前执行无环校验 |
| `run_task_asset_binding` | `node_id, asset_type, asset_id, asset_version, permission_decision_json, data_as_of_rule` | 冻结每个节点使用的指标、表、字段、数据源和权限证据 |
| `run_task_attempt` | `id, node_id, attempt_no, status, execution_id, started_at, ended_at, error_code, retry_reason` | 每次执行尝试独立记录；`UNIQUE(node_id,attempt_no)` |

| `run_claim_evidence` | `claim_id, fact_id` | 结论与执行事实多对多关系；关键结论必须至少一个事实引用 |
| `audit_plan_change` | `plan_id, from_version, to_version, actor, change_json, reason, created_at` | 记录用户/系统对计划的增删改、确认与影响分析 |

## 4. 后端修改

### 4.1 Java控制面

- 新增计划管理服务：创建、校验、版本化、差异比较、确认和作废。
- 新增DAG调度主记录和恢复协调器；服务重启从数据库恢复未终态任务。
- `PlatformExecutionService`从单次`QueryCommand`扩展为提交、计划确认、计划调整、节点重试和取消。
- `ExecutionAdmissionController`需要区分请求并发与节点执行并发，防止一个大DAG占满全局槽位；增加单请求最大并行度。
- `RuntimeFactPersistenceService`增加节点、attempt、事实、证据和计划状态落库。
- `ExecutionFactReconciler`从请求级对账升级为请求+节点级对账。
- 取消逻辑从请求级传播至运行节点和未启动依赖节点，记录传播结果。
- 增加任务级授权检查，重试不得使用旧权限绕过当前策略；需要明确是复用原快照还是强制重新鉴权。

### 4.2 Python七层执行面

- `Context`从单一`semantic_plan/sql_plan/results`升级为`task_plan/asset_bindings/executable_dag/fact_bundle`。
- L2输出多目标结构化Schema；模型输出校验失败则澄清或拒绝。
- L3新增规划器、能力注册表和确定性计划校验器。
- L4按节点批量匹配资产并返回节点级错误。
- L5新增DAG编译器、无环检查、类型检查和节点SQL计划。
- L6从`for sql_plan`顺序循环升级为受控异步调度器，支持并行、依赖、attempt、取消令牌和状态回调。
- L7输入改为`ExecutionFactBundle`，回答必须包含`evidenceRefs`和`unverifiedItems`。
- Java/Python内部OpenAPI契约需要升版，V2.0契约继续冻结用于兼容测试。

## 12. DAG通俗说明

DAG是“有向无环图”（Directed Acyclic Graph），在V2.1中表示一组任务及其前后依赖关系：

- “有向”：任务之间有明确方向，例如先查询数据，再计算同比，最后汇总结论。
- “无环”：不能出现A等B、B又等A的循环，否则任务永远无法开始。
- “图”：既可以串行，也可以并行，不局限于一条直线。

示例：用户问“对比北京、上海两家分行一季度贷款和存款，再判断哪家表现更好”。

```text
                  ┌→ T1 北京贷款 ─┐
权限与口径 T0 ────├→ T2 北京存款 ─┤
                  ├→ T3 上海贷款 ─┼→ T5 统一口径对比 → T6 证据化回答
                  └→ T4 上海存款 ─┘
```

T1—T4没有相互依赖，可以并行；T5依赖四项数据；T6依赖T5和成功事实。若T4失败，系统根据T4是否关键决定FAILED或PARTIAL_SUCCESS，并禁止把上海存款描述为已核实。

V2.1中DAG的分工是：L3设计业务任务及依赖草案，L4为各节点匹配授权资产，L5生成并校验可执行DAG，L6真正调度DAG，L7读取DAG执行事实但不修改DAG状态。

## 13. V2.1与V3.0七层逐层比较

| 层级 | V2.1：单域多任务问数 | V3.0：多域智能分析与决策协同 | 核心差异 |
|---|---|---|---|
| L1 交互与任务接入 | 接收对话、计划预览/确认、取消、重试和单域多任务请求 | 进一步接入订阅、预警、报告、分析智能体及跨域协同任务 | V2.1以用户发起为主；V3增加主动和智能体入口 |
| L2 对话/领域理解 | 抽取多个分析目标、指标、机构、时间；在已选定单域内做权限预检 | 自动识别业务领域、候选能力和跨域需求，形成跨域授权预检 | V2.1不做领域识别；V3需要识别和治理多个领域 |
| L3 语义规划 | 在单域内拆解任务、定义依赖、关键性和完整性 | 形成跨域分析路径，协调多个领域能力包、任务依赖和全局完整性 | V2.1是单域DAG；V3是多域能力驱动计划 |
| L4 可信资产匹配 | 匹配单域已发布指标、数据库表、字段及受控计算能力 | 匹配多个领域的数据库、业务API、文档、知识图谱和实时数据 | V3资产类型更多，并需要跨域授权和时效协调 |
| L5 查询与任务编排 | 生成单域SQL/受控计算DAG，执行AST、无环、类型和成本校验 | 生成跨域SQL/API/计算/检索及智能体工具组成的版本化DAG | V2.1节点类型受限；V3是异构跨域编排 |
| L6 执行与治理 | 节点串并行、限流、重试、取消、恢复、部分成功和事实持久化 | 增加跨域配额、跨系统补偿、长流程协同、域级隔离和全局任务完整性 | V3治理对象从任务节点扩展到领域和外部系统 |
| L7 证据化分析 | 汇总单域成功事实，披露失败节点和未核实项，提供受控结论 | 融合多域证据，提供综合结论、异常归因、预测和行动建议，并区分事实/推断 | V2.1侧重可靠汇总；V3侧重跨域综合分析与决策辅助 |

### 13.1 两个版本的继承关系

V2.1不是V3.0的简化命名，而是V3.0多任务底座的前置版本：

```text
V2.0 单问/少量多SQL可信流水线
  ↓
V2.1 单域任务计划、DAG和用户体验
  ↓
V2.2 智能分析和主动服务
  ↓
V2.3 单域多类型资产、治理和开放能力
  ↓
V3.0 多域能力包、跨域授权和跨域协同
```

V3.0应复用V2.1的计划版本、DAG、任务状态、重试取消、执行事实、证据链和用户交互，不重新建设另一套任务引擎；主要扩展领域标识、能力包、跨域授权、异构节点和跨域治理。

### 14.1 可以直接采用的交互结论

- 用户先看到业务说明和当前处理进展，而不是先看到技术DAG。
- 多个任务以纵向任务卡/命令卡展示；每张卡可展开参数和结果。
- 技术细节默认折叠，最终业务表格、结论、风险项和后续建议优先展示。
- 任务失败要显示具体错误；修正参数后只重新执行相关任务。
- 支持耗时显示、运行状态、执行前确认和连续追问。
- V2.1不应首先建设复杂可拖拽DAG画布；DAG是后台执行模型，前台默认使用清晰的任务列表和依赖提示。

### 14.2 三角色权限继承规则

V2.1不修改三个角色的权限定义：

- 张总：总行全机构、全指标权限。
- 李总：北京分行及下辖机构授权范围。
- 王总：总行范围内零售信贷专项指标权限。

新八场景只增加多任务组织方式，不新增角色、不扩大机构范围、不扩大指标范围。权限快照仍在请求开始时冻结，并对DAG中的每个任务节点、指标、表和字段执行校验。

当一个综合问题同时包含有权和无权任务时，为保持V2.0“全量通过”安全口径：

1. 默认不静默删除无权节点，也不直接执行剩余节点。
2. L2返回权限不足及可执行范围，整体进入`WAITING_CONFIRMATION`或`BLOCKED`。
3. 用户明确选择“仅执行有权限部分”后，系统生成新的范围收缩计划版本。
4. 新计划再次完成全节点权限校验后才能执行。

这属于V2.1多任务权限执行策略，不是角色权限重新确认。验收重点是防止任务拆解、并行、重试和上下文复用绕过V2.0权限边界。
