# AskData 产品 V2.1 需求规格说明书

> 文档版本：V0.1
> 产品版本：AskData V2.1
> 版本主题：多任务优化、用户体验、多任务执行
> 编制日期：2026-08-14
> 当前状态：需求基线稿；CR-01—CR-15已于2026-08-14按建议确认
> 适用状态：Demo、POC、Product；Customer Delivery当前为空，有客户后派生

## 1. 文档目的

本文用于冻结AskData V2.1的产品范围、业务规则、七层处理逻辑、数据和接口影响、用户体验、权限安全、非功能指标及验收标准，作为后续设计、开发、测试、验收和发布的统一依据。

本文中的要求分为三种状态：

| 状态 | 含义 |
|---|---|
| 已确认 | 已由现有V2.0基线或本阶段决策明确，开发不得自行改变 |
| 建议基线/待确认 | 已提出推荐值，需要产品确认后冻结 |
| 后续版本 | 不纳入V2.1，按V2.2、V2.3或V3.0规划 |

## 2. 产品定位

### 2.1 版本定位

V2.1定位为“单域多任务问数版本”：在V2.0企业级可信问数底座上，将一问一查或少量顺序SQL升级为综合问题理解、任务拆解、版本化计划、DAG串并行执行、节点级重试取消和证据化回答。

### 2.2 与相邻版本的关系

| 版本 | 核心定位 | 与V2.1关系 |
|---|---|---|
| V2.0 | 单域可信问数底座 | V2.1复用身份权限、资产、SQL安全、配置发布、执行事实、SSE、审计和恢复能力 |
| V2.2 | 智能分析与主动服务 | 基于V2.1可信任务事实建设异常、归因、订阅、预警和报告 |
| V2.3 | 单域数据扩展、治理和生态开放 | 增加API/文档/实时数据、模型治理、SQL助手和生态接口 |
| V3.0 | 多域智能分析与决策协同 | 复用V2.1任务引擎，增加领域能力包、跨域授权和异构编排 |

## 3. 建设目标和成功标准

### 3.1 建设目标

1. 用户可以用一个自然语言问题表达多个查询目标。
2. 系统能够在单域内形成可审计的任务计划和依赖关系。
3. 多个无依赖任务能够受控并行，有依赖任务按顺序执行。
4. 用户可以查看进度、取消请求、定位失败节点并定点重试。
5. 系统能够区分成功、部分成功、失败和取消，不隐藏未完成任务。
6. 最终结论只能引用成功执行事实，并披露未核实项。
7. V2.0权限、安全、口径和审计边界在任务拆解、并行和重试后仍然有效。
8. Demo、POC、Product同步具备V2.1能力，且V2.0演示和POC可独立恢复。

### 3.2 产品成功标准

- MT01—MT08八个新场景可在Demo中稳定重复演示。
- 八场景×三角色的正常、权限拦截和范围收缩分支符合V2.0权限定义。
- POC在真实或批准测试数据源上完成多任务执行与结果对账。
- Product通过功能、安全、容量、恢复、升级和V2.0回归门禁。
- 关键任务失败时不存在“整体正常”“完整归因”等误导性回答。

## 4. 范围与非目标

### 4.1 V2.1范围

- 单域综合问题理解和多目标抽取。
- 多任务拆解、依赖规划、关键性和完整性定义。
- 任务计划预览、确认、受控调整和版本差异。
- SQL查询、受控计算和结果汇总节点。
- DAG串行、并行、排队、超时、取消、重试和恢复。
- 任务列表、进度轨迹、部分成功、未核实项和证据展示。
- 基础任务中心。
- MT01—MT08 Demo、POC和Product同步建设。

### 4.2 明确非目标

- 多领域识别、跨域授权和跨域任务编排。
- 普通用户开放式Text-to-SQL。
- 未验证模型SQL执行或仅凭免责声明放行。
- 任意代码、任意脚本和任意外部工具执行。
- 文档检索、知识图谱和实时流数据节点。
- 开放式通用智能体或多智能体协作。
- 支付、核销、授权、关账、配置发布等高风险写操作。
- 异常预测、主动预警、订阅报告；这些属于V2.2。
- SQL助手和候选SQL审批发布；这些属于V2.3。

## 5. 用户与权限基线

### 5.1 三角色权限（已确认，保持V2.0不变）

| 角色 | 权限范围 |
|---|---|
| 张总 | 总行全机构、全指标权限 |
| 李总 | 北京分行及下辖机构授权范围 |
| 王总 | 总行范围内零售信贷专项指标权限 |

### 5.2 权限继承规则

- 请求开始时冻结用户、角色、机构、指标、表和字段权限快照。
- 每个DAG节点都必须独立校验指标、机构、表、字段和数据范围。
- 并行、重试、取消、结果复用和多轮上下文不得改变权限边界。
- 角色切换必须创建新会话和新计划，不复用旧角色事实。
- 权限或配置版本变化后，尚未执行节点必须重新校验；历史回答保留原快照用于审计。

### 5.3 混合权限问题处理（建议基线/待确认）

当一个问题同时包含有权和无权任务时：

1. 默认整单暂不执行，不静默删除无权任务。
2. 页面明确显示无权目标和当前可执行范围，但不泄露无权数据资产详情。
3. 用户确认“仅执行授权范围”后生成新的范围收缩计划版本。
4. 新计划再次完成全节点权限校验后执行。

## 6. 核心业务流程

### 6.1 自动执行流程

```text
用户提交综合问题
→ L1绑定身份、会话、配置和权限快照
→ L2抽取多个目标并校验参数/权限
→ L3拆解任务并生成计划草案
→ L4逐节点绑定可信资产
→ L5生成并验证可执行DAG
→ 符合自动执行规则
→ L6调度执行、记录事实和状态
→ L7生成证据化回答
```

### 6.2 确认后执行流程

```text
生成计划草案
→ 命中确认条件
→ 页面展示计划、范围、预计任务量和风险
→ 用户确认/调整/取消
→ 生成确认计划版本
→ 再次校验权限、安全和依赖
→ 执行
```

### 6.3 失败重试流程

```text
节点失败
→ 按错误类型判断是否可自动重试
→ 可重试且未超限：生成新attempt
→ 不可重试或重试耗尽：按关键性裁决整体状态
→ 用户手动重试时重新校验权限、配置和事实有效期
→ 只重跑失败节点和受影响下游节点
```

## 7. 第一轮：V2.1核心执行规则

以下规则已于2026-08-14按建议全部确认，作为V2.1开发基线；后续变更必须履行需求变更和影响评审。

| 编号 | 规则项 | 确认值 | 需求说明 |
|---|---|---|---|
| CR-01 | 计划调整范围 | 受控调整 | 可删除非关键节点、增加已注册节点、修改筛选条件；不得删除权限、安全、核心事实节点 |
| CR-02 | 自动执行条件 | 小型低风险计划 | 节点≤4、预计<10秒、全只读已发布能力、权限全通过时自动执行 |
| CR-03 | 强制确认条件 | 任一条件命中 | 节点≥5、预计≥10秒、高成本、范围收缩、用户要求先看计划、手动重试 |
| CR-04 | 单计划最大节点 | 10 | 超出后要求缩小问题或分轮执行；不能静默截断 |
| CR-05 | 单请求最大并发 | 3 | 超出并发的READY节点排队，执行槽释放后立即补位 |
| CR-06 | 单计划最大深度 | 5 | 防止过长依赖链和不可控等待 |
| CR-07 | 首版节点类型 | 三类 | 已发布SQL查询、受控计算、结果汇总 |
| CR-08 | 自动重试 | 最多1次 | 仅数据源临时错误、网络瞬断和可恢复超时；参数、权限、安全、口径错误不重试 |
| CR-09 | 手动重试 | 最多1次 | 仅失败且可重试节点；重试前重新校验权限、配置和事实有效期 |
| CR-10 | 取消 | 请求级幂等取消 | 取消运行节点、取消排队节点、跳过依赖节点；保留已成功事实但不生成完整结论 |
| CR-11 | 关键任务失败 | 整体FAILED | 允许展示已验证事实，但禁止完整判断、完整排名或整体正常结论 |
| CR-12 | 非关键任务失败 | PARTIAL_SUCCESS | 展示完成度、可用结论和未核实项 |
| CR-13 | 结果复用 | 有条件复用 | 权限、配置、口径、数据有效期均未变化才允许复用成功事实 |
| CR-14 | 任务中心 | V2.1基础版 | 展示运行中、成功、部分成功、失败、取消；支持查看详情和合法重试 |
| CR-15 | 控制与执行分工 | Java控制、Python执行 | Java保存计划/状态/权限/审计主记录，Python承担七层和数据任务执行 |

### 7.1 并发不等于任务数量

最大并发3表示同一时间最多运行3个任务，不表示最多只能查询3个指标。5个指标可以形成5个查询节点，其余READY节点排队：

```text
第一时刻：T1、T2、T3运行；T4、T5等待执行槽
T2完成：T4立即启动
T1完成：T5立即启动
全部关键查询完成：汇总节点启动
```

### 7.2 调度优先级（已确认）

1. 安全和权限校验节点优先。
2. 关键路径和关键任务优先。
3. 同优先级按进入READY队列时间排序。
4. 单个请求不得长期占满全局执行槽。
5. 需要同时实施全局、单用户、单请求三层并发限制。

## 8. 功能需求

### 8.1 多任务理解与规划

| 需求编号 | 需求 |
|---|---|
| FR-PLAN-001 | 系统应识别一个问句中的多个分析目标、共享机构、指标、时间和输出要求 |
| FR-PLAN-002 | 参数缺失或歧义时只询问必要条件，不生成不可执行计划 |
| FR-PLAN-003 | 系统应将综合问题拆分为可独立验证的任务节点 |
| FR-PLAN-004 | 系统应定义节点依赖、关键性、输入引用、输出Schema和完成条件 |
| FR-PLAN-005 | 计划必须无环，节点输入输出类型必须匹配 |
| FR-PLAN-006 | 每次计划调整生成新版本，保留前后差异、操作者和原因 |
| FR-PLAN-007 | 已确认计划不可原地覆盖；修改后必须重新确认和校验 |
| FR-PLAN-008 | 系统不得创建未注册任务类型或未发布查询能力 |

### 8.2 用户体验

| 需求编号 | 需求 |
|---|---|
| FR-UX-001 | 用户问题、系统说明、任务计划、执行进度和最终结果按时间顺序展示 |
| FR-UX-002 | 默认使用纵向任务列表，不以复杂可拖拽DAG画布作为主界面 |
| FR-UX-003 | 每个任务卡展示名称、状态、依赖提示、耗时和错误摘要 |
| FR-UX-004 | 参数、SQL摘要、数据来源、attempt和技术结果默认折叠，可按权限展开 |
| FR-UX-005 | 页面显示总耗时、已完成/总任务数和当前并行任务数 |
| FR-UX-006 | 等待执行槽和等待依赖必须使用不同文案 |
| FR-UX-007 | 用户可取消请求；合法失败节点提供重试入口 |
| FR-UX-008 | 部分成功必须醒目标注未核实项，不能仅在技术详情中提示 |
| FR-UX-009 | 最终回答提供结论、表格/图表、口径、数据时间、证据和推荐追问 |
| FR-UX-010 | 完整DAG关系作为高级详情可选展示，不要求首版可编辑画布 |

### 8.3 多任务执行

| 需求编号 | 需求 |
|---|---|
| FR-EXEC-001 | 调度器按照DAG依赖将节点转换为WAITING、READY、RUNNING和终态 |
| FR-EXEC-002 | 无依赖READY节点在并发限制内并行执行 |
| FR-EXEC-003 | 任一执行槽释放后，调度器立即补入下一个合法READY节点 |
| FR-EXEC-004 | 每次执行尝试形成独立attempt，不覆盖失败历史 |
| FR-EXEC-005 | 自动和手动重试不得重新生成不同SQL或扩大数据范围 |
| FR-EXEC-006 | 请求取消向运行、排队和依赖节点传播，取消操作必须幂等 |
| FR-EXEC-007 | 服务重启后从数据库恢复未终态任务，不依赖内存状态 |
| FR-EXEC-008 | 成功执行结果形成不可变事实，记录数据时间、哈希和分类等级 |
| FR-EXEC-009 | 整体状态由关键性和完成规则确定，模型不得修改 |
| FR-EXEC-010 | L7只接收成功事实，失败、跳过和取消节点进入未核实项 |

### 8.4 任务中心

| 需求编号 | 需求 |
|---|---|
| FR-CENTER-001 | 用户可查看本人运行中和历史任务 |
| FR-CENTER-002 | 支持按状态、时间和场景筛选 |
| FR-CENTER-003 | 详情可下钻请求、计划版本、节点、attempt、证据和最终回答 |
| FR-CENTER-004 | 仅当前操作者有权且状态允许时显示取消或重试按钮 |
| FR-CENTER-005 | 管理员查看范围遵循管理权限和数据脱敏规则 |

## 10. 七层处理需求

| 层级 | V2.1核心需求 |
|---|---|
| L1 | 接收问题及确认、调整、取消、重试命令；绑定会话、身份、配置和权限快照 |
| L2 | 多目标抽取、上下文补全、必填/字典/权限预检；模型只输出候选 |
| L3 | 单域任务拆解、依赖、关键性、完整性和计划版本 |
| L4 | 逐节点匹配并冻结授权指标、表、字段、数据源和口径版本 |
| L5 | 生成已发布SQL/受控计算节点，编译无环可执行DAG并执行AST安全门禁 |
| L6 | 准入、串并行、重试、取消、恢复、事件、事实和整体状态裁决 |
| L7 | 只基于成功事实输出结论、图表、证据、完成度和未核实项 |

## 11. SQL和任务能力边界

### 11.1 已确认原则

- V2.1不开放普通用户Text-to-SQL。
- 任务节点只引用已发布SQL模板和受控计算。
- 未验证模型SQL不执行、不出数、不进入回答。
- 重试复用已校验计划，不能重新让模型生成不同SQL。
- 每个SQL节点必须通过表字段权限、机构范围、参数绑定、AST只读和成本门禁。

### 11.2 允许的节点类型（已确认）

| 类型 | 是否纳入V2.1 | 说明 |
|---|---:|---|
| 已发布SQL查询 | 是 | 模板、参数、权限和AST受控 |
| 受控数学计算 | 是 | 同比、环比、差值、占比、排序、贡献度等注册函数 |
| 结果汇总 | 是 | 合并成功事实和完成度，不新增数据 |
| 只读业务API | 否，建议V2.3 | 若业务强需求，可作为V2.1增强项另行评审 |
| 文档检索/知识图谱 | 否 | V2.3及以后 |
| 任意脚本/代码 | 否 | 禁止 |
| 写操作 | 否 | 禁止 |

## 12. 数据库和数据需求

### 12.1 复用现有数据

- `run_session`、`run_request`。
- `run_layer_execution`、`run_sql_execution`、`run_provider_execution`。
- `run_sse_event`、`run_result_snapshot`。
- 权限、资产、流程场景、审计、保留和归档表。

### 12.2 新增核心数据

- 任务计划及计划版本。
- 任务节点和依赖边。
- 节点资产绑定和权限决定。
- 节点执行attempt。
- 不可变执行事实。
- 回答结论和事实证据关系。
- 计划修改、确认、取消和重试审计。

建议表清单：`run_task_plan`、`run_task_node`、`run_task_dependency`、`run_task_asset_binding`、`run_task_attempt`、`run_execution_fact`、`run_answer_claim`、`run_claim_evidence`、`audit_plan_change`。

### 12.3 数据迁移要求

- 只允许新增Flyway迁移，不修改V1—V16历史迁移。
- 新表初始为空，不改变V2.0历史请求含义。
- 现有单请求可在读取时映射为单节点兼容视图，但不强制回填历史DAG。
- 迁移必须支持空库、V2.0升级、回退恢复和双数据库测试。

|---|---|---|
| POST | `/api/v2.1/requests` | 提交综合问题 |
| GET | `/api/v2.1/requests/{id}/plan` | 查询计划 |
| PUT | `/api/v2.1/requests/{id}/plan` | 受控调整并生成新版本 |
| POST | `/api/v2.1/requests/{id}/confirm` | 确认计划 |
| GET | `/api/v2.1/requests/{id}/events` | SSE任务事件与断线续传 |
| POST | `/api/v2.1/requests/{id}/cancel` | 幂等取消 |
| POST | `/api/v2.1/tasks/{taskId}/retry` | 定点重试 |
| GET | `/api/v2.1/requests/{id}/answer` | 获取证据化回答 |

Java/Python内部契约必须升版并冻结Schema；新增字段不得依赖自由格式JSON才能理解核心状态。

## 14. 管理端需求

- 场景配置增加MT01—MT08、任务模板、依赖、关键性和演示分支。
- 流程配置增加任务类型、DAG模板、超时、重试、并发和完整性策略。
- 数据字典维护节点输入输出Schema、指标口径和数据时效。
- 用户权限不新增角色，但增加任务能力权限映射和节点级权限审计。
- 模型配置增加多目标抽取Schema和L7证据解释能力检查。
- 系统运维增加任务队列、节点状态、重试、取消、部分成功和成本监控。
- 查询日志支持request→plan→node→attempt→SQL→fact→claim→evidence下钻。

## 15. 非功能需求

### 15.1 性能和容量（建议基线/待压测确认）

- 全局执行并发沿用V2.0默认30个执行槽，需重新定义请求槽与任务节点槽的关系。
- 单用户节点并发建议6，单请求节点并发建议3。
- 单计划最大10个执行节点、最大深度5。
- 队列满快速拒绝，不允许无限排队。
- SSE支持断线续传和心跳；任务事件顺序按request单调递增。
- 正式阈值必须通过短时峰值和长稳测试后冻结。

### 15.2 可靠性

- 服务重启后恢复未终态任务。
- 成功节点在权限、配置、口径和数据有效期一致时不得重复执行。
- 调度、重试和取消必须幂等。
- 数据库、发布包和秘密恢复材料必须形成不可拆分恢复点。

### 15.3 安全

- 所有节点只读，禁止DDL/DML和任意代码。
- 权限检查至少覆盖L2业务目标、L4资产和L5 SQL范围三道门禁。
- 日志、事件和结果不得泄露凭据或未脱敏敏感数据。
- 重试、结果复用和计划调整必须重新验证安全前提。
- 输出文本必须复核机构、指标、时间和数值均来自成功事实。

### 15.4 可观测性

- 统一`traceId/requestId/planId/taskId/attemptId`。
- 指标覆盖队列深度、DAG节点数、并行度、节点成功率、重试率、取消延迟、部分成功率和关键路径耗时。
- 告警覆盖积压、关键失败、取消超时、重试风暴、孤儿节点和事实/回答不一致。

## 17. 测试和验收需求

### 17.1 测试矩阵

- 单元：拆解、无环、拓扑、关键性、状态裁决、重试、取消和复用。
- 契约：L1—L7、Java/Python内部契约、外部API和SSE续传。
- 权限：三角色×八场景，覆盖并行、重试、角色切换和混合权限。
- 安全：SQL绕过、计划注入、提示注入、重试换SQL和输出泄露。
- 集成：MT01—MT08正常、部分成功、失败、取消和重试分支。
- 性能：宽DAG、深DAG、长任务、并发用户、公平性和事件量。
- 恢复：控制面/执行面重启、数据库恢复和发布回退。
- 回归：V2.0 S01—S08、三角色和Demo/POC恢复能力。

### 17.2 发布门禁

- 第一轮核心执行规则全部确认并落入契约/配置。
- 不存在P0/P1缺陷。
- Demo、POC、Product三类制品分别验收并保留SHA256。
- RC制品验收后原样晋升，不重新构建。
- V2.0稳定标签和制品可独立获取与启动。

## 18. 兼容、升级和回退

- V2.0接口和数据不因V2.1上线失效。
- V2.1通过新版本接口或显式能力开关启用。
- V2.1失败不得影响V2.0 Demo/POC启动。
- 数据库升级前生成完整恢复点；回退必须同时恢复应用、数据库和秘密材料。
- 新版前端遇到不支持V2.1的后端时，应隐藏多任务入口并给出版本提示。
