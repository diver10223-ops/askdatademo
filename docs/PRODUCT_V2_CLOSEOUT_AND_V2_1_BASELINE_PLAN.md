# V2.0内容判定、提交发布与V2.1开发基线建立计划

## 1. 结论

V2.1开发前必须先关闭V2.0。正确顺序如下：

```text
V2.0工作区内容判定
→ 分批整理和提交
→ V2.0测试、验收和发布关闭
→ 冻结V2.0 Demo/POC/Product制品与正式标签
→ 从V2.0正式Product标签创建V2.1开发分支
→ 使用独立worktree、端口、数据库和数据目录启动V2.1
```

当前HEAD为`9b068f6`，最近稳定演示/POC标签为`v1-v2-poc-baseline-20260812`；工作区存在大量已修改和未跟踪内容，不能直接作为V2.1基线，也不能一次性无分类提交。

## 2. V2.0内容判定规则

每个工作区文件必须归入以下一种：

| 分类 | 判定标准 | 处理 |
|---|---|---|
| V2.0产品实现 | V2.0控制面、执行面、安全、容量、恢复、交付和发布必需 | 纳入V2.0提交和门禁 |
| V2.0测试/发布证据 | 测试、契约、迁移、部署、手册、Release Notes | 纳入对应测试/文档提交 |
| V2.1—V3规划 | 新版本需求、场景、架构和路线图，不改变V2.0运行 | 独立规划文档提交，不混入V2.0运行提交 |
| 生成制品 | PPT、DOCX、PDF、截图等可交付物 | 保留源、版本和校验值；按仓库制品策略决定是否入Git |
| 运行/临时文件 | PID、日志、本地数据库、缓存、构建临时文件 | 排除并补充`.gitignore`，不得进入产品提交 |
| 不确定/冲突 | 无法确认版本归属或与现有修改重叠 | 暂不提交，建立待判定清单 |

## 3. 建议提交批次

1. V2.0运行实现：Java、Python、配置和数据库迁移。
2. V2.0安全与契约：认证过滤、内部/外部OpenAPI、依赖和安全门禁。
3. V2.0测试：Java/Python测试及测试环境配置。
4. V2.0发布和运维：部署、迁移、恢复、容量、安全和打包脚本。
5. V2.0产品文档：用户、管理员、安全、Release Notes和交付说明。
6. V2.1—V3规划文档及生成源：与V2.0代码提交分离。
7. 仓库卫生：`.gitignore`和开发容器调整，说明影响并单独提交。

每批提交前执行`git diff --check`、秘密扫描和对应最小测试；每批提交后记录提交号和文件范围。

## 4. V2.0发布关闭条件

- 工作区内容全部完成归属判定，正式发布提交工作树干净。
- V2.0自动测试、安全门禁、容量、迁移、备份恢复和长稳要求通过。
- Demo、POC、Product状态分别形成结论，不把客户交付写成已完成。
- Demo、POC、Product三类版本化制品生成Manifest、SBOM（适用时）和SHA256。
- 从制品而非源码目录完成离线验证、冷启动、升级和恢复演练。
- Release Notes列明环境中立产品基线、客户未知项和已知限制。
- 创建不可移动正式标签，例如`product-v2.0.0`，并推送远端和制品库。
- Customer Delivery保持为空。

## 5. V2.1开发基线

V2.0正式关闭后执行：

1. 从`product-v2.0.0`创建`develop/product-v2.1`。
2. 建立独立worktree，不占用V2.0维护工作目录。
3. 使用独立端口、数据库、数据目录、Fixture和制品目录。
4. 初始化V2.1需求—设计—任务—测试追踪矩阵。
5. 冻结V2.1 CR-01—CR-15、状态机、错误码、七层契约和数据库逻辑模型。
6. 先实施MT01最小闭环，再逐步完成MT02—MT08。
7. V2.0维护修复只能经完整门禁选择性前向合入V2.1；V2.1功能不得反向污染V2.0。

## 6. V2.2和V2.3基线规则

- V2.2从V2.1正式Product标签创建，不从V2.1开发分支创建。
- V2.3从V2.2正式Product标签创建，不从V2.2开发分支创建。
- 每次建立新基线前，前一版本Demo、POC、Product均已冻结并可独立恢复。
- 每个版本使用独立开发/发布分支、数据库迁移段、初始化数据版本和测试证据。
