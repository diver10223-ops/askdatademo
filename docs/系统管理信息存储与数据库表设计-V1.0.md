
# NLQ智能银行问数平台：系统管理信息存储边界与数据库表设计

> 版本：V1.0  
> 日期：2026-08-12  
> 目标平台库：MySQL 8.0；当前POC兼容：SQLite  
> 范围：系统管理元数据，不包含客户业务事实数据

### 已确认建设口径

- 单租户，不在业务表增加 `tenant_id`；
- 前端问数使用者规模为10万至100万级；
- 支持LDAP、OIDC、SAML等统一身份认证，平台保存外部身份映射，不保存统一认证密码；
- 权限申请、配置发布、模型/数据源启用、敏感数据访问等支持审批；
- 系统存在并发访问要求，运行态数据不得继续依赖单机SQLite；
- 峰值同时在线100人，峰值登录200 QPS，峰值问数提交200 QPS；
- 最大执行并发30至50，最大SSE连接1,000，每日问数20,000；
- 问数响应目标为P95不超过15秒、P99不超过30秒；
- 200 QPS按入口短时突发能力设计，不代表下游可持续执行200 QPS；持续时间、允许排队时间和超载拒绝比例仍须通过压测定标。

## 1. 结论

系统管理信息不能继续主要依赖前端种子、通用JSON资源表或基线配置文件。常规原则如下：

- 需要后台增删改查、多人共享、关联校验、审批发布、动态生效、回滚审计的信息，应进入数据库。
- 服务连接数据库之前就必须知道的参数、与服务器实例绑定的部署参数，应保留在环境变量或配置文件。
- API Key、数据库密码可以在数据库保存应用层加密后的密文；加密主密钥不得进入数据库，应放在密钥管理系统或权限为600的环境文件。
- 官方基线JSON可以保留为首次初始化和灾难恢复种子，但不能作为日常编辑的唯一事实源。
- 客户贷款、客户、交易等业务事实仍保存在ClickHouse/MySQL业务数据源，不进入平台管理库。

### 3.1 百万级用户总体架构

建议把“身份目录”和“问数运行链路”分开设计：

~~~text
统一身份提供方（OIDC/SAML/LDAP）
          │ 登录、令牌校验、用户增量同步
          ▼
认证接入层 ── Redis集群（令牌/会话/限流/短期上下文）
          │
          ├── MySQL高可用集群：用户映射、角色权限、配置、审批
          ├── 请求执行队列：削峰、并发隔离、取消
          ├── ClickHouse/MySQL业务源：只读问数
          └── 日志/事件存储：运行日志分区、归档或专用分析库
~~~

关键原则：

1. 统一身份提供方负责认证，平台负责授权；不得为百万用户重复维护统一认证密码；
2. 登录时使用外部主体标识建立或更新本地影子用户，不能每次请求实时查询LDAP；
3. 访问令牌验证、本地Session、限流计数和短期上下文放在Redis集群，不把高频状态全压到MySQL；
4. MySQL采用主从或高可用集群，配置与权限读请求可使用只读副本，但发布和授权变更必须走主库；
5. 问数请求异步化并设置用户、角色、模型、数据源四级并发限制，防止下游Provider被流量击穿；
6. SSE事件和运行日志设置短期在线保留，过期归档，不能无限堆积在主交易库；
7. 应用服务应无状态横向扩展；本地内存不得作为唯一Session、取消状态或限流状态；
8. 用户规模不等于并发容量；本项目按已确认指标设计，并通过压测验证入口突发、执行并发、排队和P95/P99目标。

## 5. 身份权限表设计

### 5.1 `iam_org`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `parent_id` | BIGINT UNSIGNED | FK→iam_org.id，可空 |

| 通用审计字段 |  | 见3.2 |

索引：`UK(code)`、`IDX(parent_id,sort_no)`、`IDX(path(191))`。

### 5.2 `iam_user`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `username` | VARCHAR(64) | UK，登录账号 |
| `display_name` | VARCHAR(128) | 姓名 |
| `user_type` | VARCHAR(20) | ADMIN/BUSINESS/SERVICE |
| `org_id` | BIGINT UNSIGNED | FK→iam_org |
| `mobile_cipher` | VARBINARY(512) | 手机密文 |
| `mobile_hash` | BINARY(32) | 手机精确检索HMAC |
| `email` | VARCHAR(254) | 可空 |
| `auth_source` | VARCHAR(32) | LOCAL/LDAP/OIDC/SAML |
| `external_subject` | VARCHAR(191) | 外部身份ID |
| `password_hash` | VARCHAR(255) | 本地认证哈希，禁止明文 |
| `failed_login_count` | INT | 默认0 |
| `locked_until` | DATETIME(3) | 锁定截止 |
| `last_login_at` | DATETIME(3) | 最近登录 |
| `status` | VARCHAR(20) | ENABLED/FROZEN/DISABLED |
| 通用审计字段 |  | 见3.2 |

百万级用户设计要求：

- `username`仅在对应认证域内唯一，建议增加 `identity_provider_id` 后使用唯一键 `(identity_provider_id, external_subject)`；
- 用户同步采用全量初始化加增量事件/定时同步，不在登录高峰执行全目录扫描；
- 用户列表使用基于主键的游标分页，禁止百万级数据使用大偏移 `OFFSET`；
- 用户状态、机构、认证源分别建立组合索引：`(status,id)`、`(org_id,status,id)`、`(identity_provider_id,external_subject)`；
- 频繁变化的最近访问时间不直接逐请求更新用户主表，应在Redis聚合后异步批量回写；
- 离职、冻结和角色撤销事件需主动使令牌、Session及权限缓存失效。

### 12.1 高并发运行态拆分

百万用户规模下，不建议把所有运行态数据都同步写入同一个MySQL主库：

| 数据 | 在线载体 | 持久化策略 |
|---|---|---|
| 登录Session、令牌撤销、权限版本 | Redis集群 | 必要摘要异步入库 |
| 问数短期上下文 | Redis集群，设置TTL | 关键上下文随Session快照入库 |
| 用户/角色/API限流 | Redis原子计数或令牌桶 | 告警和违规事件异步入库 |
| 请求主记录及终态 | MySQL主库 | 创建和终态必须持久化 |
| 分层、模型、SQL日志 | 消息队列后批量写入 | 允许秒级最终一致 |
| SSE事件 | Redis Stream/专用事件层 | 仅短期续传，终态后过期 |
| 大结果快照 | 对象存储或结果存储 | MySQL保存URI、摘要、大小、过期时间 |
| 历史运行分析 | 日志分析库/ClickHouse | 从消息流或归档同步 |

相应建议增加：

- `run_result_snapshot.storage_type`：INLINE/OBJECT_STORAGE；

### 12.3 容量基线与压测门槛

### 12.3.1 已确认容量指标

| 指标 | 目标值 | 设计解释 |
|---|---:|---|
| 注册/可服务用户规模 | 100,000–1,000,000 | 统一认证影子用户总量 |
| 峰值同时在线 | 100 | 活跃交互用户，不等于SSE容量上限 |
| 峰值登录QPS | 200 | 认证入口短时突发；令牌校验尽量本地完成 |
| 峰值问数提交QPS | 200 | API接收短时突发，须通过队列削峰 |
| 最大并发执行数 | 30–50 | 模型与数据源真实同时执行上限 |
| 最大SSE连接数 | 1,000 | 含断线重连、多个页面及运维余量 |
| 每日问数总量 | 20,000 | 平均约0.23 QPS，流量高度突发 |
| P95响应时间 | ≤15秒 | 从提交成功到业务终态，原则上包含排队 |
| P99响应时间 | ≤30秒 | 从提交成功到业务终态，原则上包含排队 |

### 12.3.2 指标一致性分析

按Little定律做简化估算：

- 执行并发50、平均占用15秒时，稳态吞吐约为 `50÷15=3.33请求/秒`；
- 执行并发30、平均占用15秒时，稳态吞吐约为 `30÷15=2请求/秒`；
- 即使按30秒计算，并发50也只能长期稳定处理约1.67请求/秒；
- 因此200 QPS不能被解释为持续执行吞吐，只能是入口瞬时突发接收能力。

如果200 QPS持续1秒，将产生约200个请求。执行槽位50且单次约15秒时，最后一批至少经历4个批次，理论完成时间约60秒，已经无法满足P99 30秒；并发30时情况更明显。因此必须采用以下合同口径之一：

1. **推荐口径：**200 QPS是短时入口峰值，系统接收后对超出30–50执行槽位和P99可承载队列的请求快速返回“系统繁忙/请稍后重试”；
2. 200 QPS全部接收，但排队请求不计入15/30秒响应SLA；此口径用户体验和SLA定义较弱；
3. 若要求200 QPS全部完成且P99≤30秒，必须把模型、数据源和应用有效并发提高到约3,000以上（按15秒占用粗估），这与当前30–50并发目标冲突。

本设计采用第1种口径：入口可抗200 QPS短突发，但只有进入受控执行队列并被接受的请求适用业务响应SLA；超载请求应在1秒内明确拒绝，不进入无限队列。

### 12.3.3 队列容量和超载规则

建议初始值如下，最终以压测调整：

| 参数 | 初始建议 | 说明 |
|---|---:|---|
| 全局执行并发 | 50 | 可按模型和数据源较小值动态降低到30 |
| 单用户执行并发 | 2 | 避免单用户占满资源 |
| 等待队列上限 | 50 | 与执行槽位1:1，防止排队时间失控 |
| 最大允许排队时间 | 5秒 | 超过即返回过载状态 |
| 提交API处理P99 | ≤1秒 | 不包含问数业务执行 |
| 超载响应 | HTTP 429或503 + `Retry-After` | 区分用户限流与系统过载 |
| 幂等窗口 | 60秒 | 防止客户端重试形成重复请求 |
| SSE重连退避 | 1、2、4、8秒并加随机抖动 | 防止重连风暴 |

按“50执行中+50排队”计算，最多接受100个未完成问数请求。200 QPS突发时，其余请求必须快速拒绝或由上游控制流量。队列上限应根据实测平均执行时间动态调整，不能只按用户总量扩大。

### 12.3.4 SSE容量设计

- 应用实例无状态部署，SSE连接可按一致性哈希或共享Redis Stream恢复，不依赖单机内存事件；
- 1,000连接建议至少预留30%容量，即压测到1,300连接；
- 每个用户和Session限制SSE连接数，关闭页面后及时释放；
- 心跳间隔建议15–30秒，事件保存时间覆盖最大断线续传窗口；
- 压测连接建立、心跳、事件推送、断线续传及1,000连接同时重连；
- 文件描述符、反向代理虽本期不用，但操作系统连接队列、keepalive和端口资源仍须配置。

### 12.3.5 登录峰值设计

峰值登录200 QPS高于同时在线100，按批量重新认证或故障恢复突发处理：

- OIDC/SAML优先使用本地JWKS缓存验证令牌，不能逐请求访问认证服务；
- LDAP模式使用受控连接池、短期认证结果缓存和熔断，禁止把目录密码落库；
- JIT用户创建使用外部主体唯一键和幂等写入，避免并发重复建用户；
- 登录事件异步写入，主登录链路不等待审计分析库；
- JWKS刷新失败时使用未过期缓存并告警，超过安全窗口后拒绝认证。

### 12.3.6 日容量与存储估算

每日20,000个问数请求，按每请求7条分层记录、2条SQL/Provider记录估算：

- `run_request`：约2万行/日，730万行/年；
- `run_layer_execution`：约14万行/日，5,110万行/年；
- SQL、模型和数据源调用记录合计：约4万至8万行/日；
- SSE事件和结果快照体积受输出大小影响最大，必须实测平均及P99大小。

运行明细表应按月分区或按月归档。主交易库保留最近3至6个月在线数据，历史日志同步到ClickHouse或归档存储；结果快照根据数据等级保留7至90天。

### 12.3.7 压测放行门槛

至少执行阶梯加压、200 QPS短突发、30/50执行并发、1,300 SSE连接、30分钟峰值、8小时长稳、下游超时、模型限流、数据源故障和恢复测试。

| 指标 | 建议放行值 |
|---|---|
| 已接受问数请求P95/P99 | ≤15秒 / ≤30秒 |
| 提交API P99 | ≤1秒 |
| 登录入口200 QPS时错误率 | ≤0.1%，不含外部身份方主动拒绝 |
| 正常容量内问数失败率 | ≤1%，不含业务权限拦截 |
| 超载请求反馈 | 1秒内明确429/503，不超时悬挂 |
| SSE连接 | 1,300连接稳定，事件不乱序、不重复丢失 |
| 取消请求 | 5秒内传播至队列/Provider，成功率≥99% |
| 审计与日志 | 主链路不因异步日志阻塞；最终丢失率为0 |
| MySQL主从延迟 | 正常≤1秒；发布/授权读主库 |
| Redis和队列 | 无不可恢复积压，节点故障可自动恢复 |

## 14. 关键约束与索引

1. 已启用表必须属于已启用数据源；
2. 已启用指标映射必须引用已启用表和字段；
3. 运行组合只能引用已启用且诊断成功的模型、数据源；
4. 场景的SQL、指标和数据表必须属于同一可发布配置；
5. PHASE2_POC禁止Fixture降级；
6. REVOKED秘密被引用时，模型或数据源不得启用；
7. 发布只影响新Session；Session必须保存权限和配置快照；
8. 被引用资源不得级联物理删除，应先禁用；
9. 审批、审计和运行日志禁止业务管理员物理删除；
10. 编码发布后原则上不可修改；
11. 所有编码建立唯一索引，所有外键建立索引；
12. 列表常用`(status,updated_at)`，日志常用`(created_at,status)`；
13. 大TEXT/JSON不直接作为筛选字段，应把筛选维度列化；
14. 个人信息精确检索使用HMAC哈希列，不索引密文。

## 15. MySQL建库基线

~~~sql
CREATE DATABASE askdata_platform
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

CREATE USER 'askdata_app'@'APP_SERVER_IP'
  IDENTIFIED BY '由密码管理系统生成';

GRANT SELECT, INSERT, UPDATE, DELETE
  ON askdata_platform.* TO 'askdata_app'@'APP_SERVER_IP';

-- DDL迁移账号必须单独创建，应用账号不授予建表、删表权限。
~~~

建议使用Alembic管理版本化DDL，禁止普通应用账号在启动时任意变更表结构。

## 16. SQLite到MySQL映射

| SQLite | MySQL 8.0 | 说明 |
|---|---|---|
| TEXT主键 | BIGINT/CHAR(26)/CHAR(36) | 项目统一ID策略 |
| INTEGER布尔 | TINYINT(1) | 0/1 |
| TEXT JSON | JSON | 仍需应用Schema校验 |
| ISO时间TEXT | DATETIME(3) | UTC |
| REAL | DECIMAL或DOUBLE | 金额必须DECIMAL |
| AUTOINCREMENT | AUTO_INCREMENT | 日志流水 |
| 部分唯一索引 | 当前发布指针表 | MySQL无直接等价 |
| PRAGMA外键 | InnoDB外键 | 正式表使用InnoDB |

## 18. 实施顺序

本节描述数据库建设的设计依赖，不作为产品V2.0的独立执行入口。实际任务编号、先后顺序、状态和门禁统一以`PRODUCT_V2_EXECUTION_PLAN.md`为准。

1. 冻结基线JSON、运行默认配置和前端seeds；
2. 明确统一认证协议、外部主体标识、机构/组属性映射和令牌生命周期；
3. 建立MySQL高可用平台库、Redis集群、消息队列、迁移账号和应用账号；
4. 创建身份权限、认证映射、资产、模型数据源、流程场景、安全运维和审批表；
5. 执行统一身份目录初始化同步，验证增量同步、冻结和缓存失效；
6. 编写一次性导入程序，把前端seeds和基线转换为规范化记录；
7. 核对数量、编码、权限、映射和场景轮次；
8. 生成首个`cfg_release`并计算SHA256；
9. 后台API改为读写规范化表，不再依赖前端seeds；
10. `admin_resources`进入只读兼容期；
11. 迁移会话、日志、审批和Provider数据，并把高频状态迁至Redis/队列；
12. 执行三角色八场景、统一认证、权限审批、发布回滚和备份恢复；
13. 按目标容量进行阶梯、突发、长稳和故障压测；
14. 停止通用JSON写路径，仅保留官方基线作灾难恢复；
15. 在目标环境进行回滚演练和签字验收。

## 19. 不建议的方式

- 继续用`admin_resources(kind,id,payload)`承载所有管理对象；
- 用逗号字符串保存角色、表或字段列表；
- 在前端源码中维护后台业务数据；
- 把动态业务配置与服务器启动配置混在同一`.env`；
- 把明文密码、API Key、完整连接串写进快照或日志；
- 以JSON快照作为唯一事实源；
- 让应用运行账号拥有DDL和授权权限；
- 把客户大规模业务事实放入平台管理库。

## 20. 进入DDL实施前待确认

1. 正式平台数据库是否确定为MySQL 8.0；
2. 统一认证最终采用OIDC、SAML还是LDAP，以及外部唯一主体字段；
3. ID采用BIGINT、UUID还是ULID；
4. 各类权限和配置发布的审批人、会签方式及超时时间；
5. 各类日志、结果和审计的合规保留周期；
6. 手机、邮箱、姓名的加密与检索要求；
7. 200 QPS峰值预计持续时间，以及超载请求采用快速拒绝还是排队不计入SLA；本设计暂按快速拒绝；
8. 平台库、Redis、消息队列是否要求跨机房高可用和灾备；
9. 是否引入专用密钥管理系统；
10. `admin_resources`兼容期和下线日期。

已确认不需要多租户，因此本设计不增加`tenant_id`。如果未来改变为多租户，必须作为架构变更重新评审，不能只追加一个字段。
